# 创意脚本

## 核心目标

让观众先产生“我必须知道接下来会怎样”的冲动，再用人物选择、因果升级和情绪兑现完成一篇独立成立的故事。默认创作原创内容；借鉴类型机制，不复刻在世作者的独特文风、具体角色或标志性桥段。

## 开始前

从用户信息中提取：载体、题材、受众、篇幅、基调、视角、必须保留的设定、禁区和期望交付物。信息不足时，仅在缺失项会根本改变作品时提问；否则明确一句关键假设并直接创作。

根据任务按需读取参考资料：

- 需要挑选 Hook、倒叙、反转或完整结构时，读取 `references/hook-and-structure.md`。
- 创作网文、短故事或追求强追读感时，读取 `references/web-fiction.md`。
- 创作游戏主线、任务、角色对话、分支或多结局时，读取 `references/game-narrative.md`。

## 创作流程

### 1. 锁定情绪承诺

用一句话写清观众最终应得到的主要体验，例如“被忽视的小人物终于被看见”“每次拯救都要牺牲一段记忆”。选择一种主情绪和一种余味；不要让所有情绪平分篇幅。

### 2. 生成并筛选 Hook

先在内部生成至少 5 个不同机制的候选 Hook，再选最强者。优先组合以下两到三项：

- 熟悉处境：账单、亲情、尊严、孤独、亏欠、职场、身份焦虑。
- 反常变化：规则突然失效、关系颠倒、秘密暴露、时间错位。
- 明确代价：倒计时、失去某人、暴露身份、不可逆选择。
- 信息缺口：观众知道结果却不知道原因，或知道危险而角色不知道。
- 独特动作/画面：可在开场被看见，而不只是被解释。

用四项淘汰弱 Hook：能否被一句话复述；是否立刻影响具体人物；是否承诺后续变化；结局能否兑现或反转它。拒绝只有怪异设定、没有人物代价的伪 Hook。

### 3. 建立故事引擎

写出一条因果链：

`主角缺口 → 触发事件 → 可见目标 → 阻力升级 → 被迫选择 → 代价 → 新选择 → 结局兑现`

同时定义：

- 主角想要什么（外部目标）。
- 主角真正需要什么（内部改变）。
- 为什么偏偏是现在。
- 什么力量持续制造压力。
- 成功与失败各失去什么。
- 主角最终做出的不可替代选择。

每个主要转折必须由之前的选择、误判或线索造成。巧合可以引爆故事，不能替主角解决故事。

### 4. 选择结构

默认使用线性因果结构。只有在改变信息顺序能增强悬念、反讽或情感时，才使用倒叙、多线或碎片化结构。

- 小切口：从一件具体物品、一次误会、一笔小钱、一句没发出的消息或一个日常任务切入，让它逐步连到更大的关系或世界问题。
- 倒叙：先展示一个不可逆结果，再返回关键起点；中段不断改变观众对开场的理解，结尾必须为开场补上新的情感含义。
- 双线：两条线必须互相提供因果、误导或情绪镜像，并在汇合时产生第三层意义。
- 游戏分支：先设计共享主干，再让选择改变资源、关系、信息或伦理代价；避免只有台词不同的假分支。

### 5. 排列节拍与场景

为每个场景写一个简短场景卡：`目的 / 冲突 / 新信息 / 选择或变化 / 离场钩子`。删除不能改变人物处境、认知、关系或计划的场景。

控制升级：压力至少在时间、关系、风险、道德、身份或资源中的一个维度变大。反转后必须改变下一步行动，而非只制造惊讶。

篇幅建议：

- 短篇：1 条主冲突、1 条人物关系、1 次核心反转、1 个完整回收。
- 中篇：1 条主线，最多 2 条服务主线的副线；每一幕都有局部目标、阶段失败或代价。

### 6. 写成可用脚本

除非用户只要大纲，默认交付完整剧情脚本而非停在策划说明。使用适合载体的格式：

- 叙事短篇/网文：场景化正文，减少背景说明，尽早进入动作、对话或异常。
- 影视/短视频：场次标题、时空、动作、人物名与对白；把可见可听内容写在页面上。
- 游戏：节点/任务目标、触发条件、场景动作、对白、玩家选择、状态变化与结果；共享信息与分支信息分开标注。

对白要让不同角色具有不同欲望与策略。让潜台词承担关系冲突；避免所有人都直接说出主题和背景。

### 7. 完成闭环

结局必须同时处理：外部目标、人物内部缺口、核心关系、开场承诺、重要伏笔。开放式结局可以保留未来不确定性，但当前故事的关键选择与情绪问题必须得到回答。

### 8. 交付前自检

- 前 10% 是否出现人物、异常/冲突和具体代价？
- Hook 是否在结局被兑现、加深或反转？
- 每次升级是否源自主角行为或已建立的力量？
- 中段是否产生新的问题，而非重复阻挠？
- 反转是否“意外但回看必然”，且有公平线索？
- 主角是否通过选择改变结局，而非被设定推着走？
- 场景是否有进入目的和离场变化？
- 是否删掉解释性重复、空泛金句和无后果支线？
- 最后一个画面/动作是否承载余味，而非用总结代替情感？

发现缺陷时直接修订成稿，不把自检过程倾倒给用户。除非用户要求，交付时只给一句创意定位、必要的角色表和作品正文；避免冗长讲解削弱阅读体验。
